## 小游戏的规则写在哪

没有单独的设计文档 —— 数值就写在代码常量的位置上，改一个数只改一处：

| 游戏 | 文件 | 说明 |
|---|---|---|
| 弹跳得分 | `game/minigame.py` | 方块布局、起跳初速、60 秒单局、通关加时、方块耐久/连击/掉落道具 |
| 接狗狗 | `game/catcher.py` | 血量上限、扣血规则、连击奖励、难度爬升、两条出怪保底 |
| 跑一跑（v2.2.0） | `game/runner.py` | 障碍种类与尺寸、难度分档（速度/间距）、跳跃缓冲与可变跳高、判定盒收窄 |
| 狗粮 2048（v2.2.0） | `game/g2048.py` | 目标格子、撤销次数、金币折算（**按最大格子**，另一把尺子）|
| 共用部分 | `game/common.py` | 窗口尺寸、HUD 高度、地面厚度、中文字体回退链、结算浮层、**HUD 排版算术**（`zone_spans` 等）|

写进报告时建议直接引 `game/catcher.py` 开头那段 docstring —— 那里把
"为什么复用 `Motion`""为什么缺素材也能玩""为什么难度只看存活时间"三个取舍都写了。
**反过来**，`game/runner.py` 的 docstring 里写了本项目第一次"**该复用却不复用** `Motion`"
的理由（单向运动十行算术就够），也是一处可以引的取舍。

> `game/g2048.py` 与 `game/runner.py` 的**规则层都不 import Qt**（`slide_line` / `move` /
> `can_move` / `is_finished` / `coins_for_tile` / `pattern_width` / `speed_for` 等全是纯函数），
> 就是为了能单测 —— 2048 的"死局"这条路径在窗口层很难构造。

## 卡册系统的依据（v2.3.0）

抽卡那套数字**不是拍脑袋定的**，是蒙特卡洛模拟出来的，所以把推导过程一起放进来：

| 文件 | 说明 |
|---|---|
| `抽卡参数方案.md` | v1.1 定稿：出率 / 抽卡价 / 分解与兑换价 / 周额度 / 保底 / 装备加成全部取值的推导，含"为什么梯度要靠兑换价掰""为什么装备不是加速器"两条结构性结论 |
| `卡片分档.csv` | 102 张素材的分档结果（107 行 —— 含被剔除的 5 张，理由见方案文档第八、九节）|

`assets/cards/cards.json` 就是按 `卡片分档.csv` 生成的（脚本见 `assets/cards/README.md`）。
**改数值之前先读 `抽卡参数方案.md`** —— 里面每一个数都标了它牵动什么，
而 `tools/check_cards.py` 会把改坏的规则直接测出来。

> 卡池素材（102 张线条小狗）来自爱给网，分档由人眼逐张过 ——
> 白狗身体是透明的，程序识别不出"穿没穿衣服"，只能看。
